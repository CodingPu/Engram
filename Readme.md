# Engram - 个人知识引擎

> Karpathy 的 LLM Wiki 只走了一半。知识库再精美，你自己脑子里没有，它就只是一本更好看的书。Engram 补上另一半。

**一句话：** 自托管的个人知识引擎。LLM 维护 Wiki → 多种学习活动 → AI Bot 主动推送（文字+语音），知识不是搜的，是找你的。

## 核心特性

Engram 把三件事拼在一起：

| 组件 | 说明 |
|------|------|
| **LLM Wiki** | AI 增量构建和维护结构化知识库（Karpathy 方案升级版）|
| **间隔重复** | 不是 Q/A 卡片，而是费曼挑战、连接、应用等多种主动回忆模式 |
| **多通道推送** | 终端、QQ、Telegram，文字+语音，知识主动找你 |

**核心哲学：** 你的大脑是第一海马体，Wiki 是第二海马体。两者之间需要一条主动回忆的传输通道——不是搜索，不是浏览。没有它，知识库就是图书馆；有了它，才是学习机器。

## 为什么不用 Anki

**问题的本质：** Anki 的间隔重复原理是对的，但交互设计有结构性缺陷。

| 问题 | 影响 | Engram 方案 |
|------|------|----------|
| **识别 ≠ 理解** | 看到问题等答案出现，大脑在做模式匹配，不是真理解 | 费曼式生成任务，自己写出来 |
| **无输出** | 只认出答案，不生成答案 | 多种活动模式，都需要主动输出 |
| **碎片化** | Q/A 对孤立，丢失关系和上下文 | Wiki 是图形化的知识网络 |
| **摩擦大** | 需要专门打开 app，时间成本高 | 主动推送到 QQ/终端，零主动成本 |
| **积压劝退** | 200 张待复习一看就崩溃 | 微习惯设计：默认每天 1 个，可选加量 |
| **考试心态** | "请回答问题"，本能逃避被评判 | 朋友请教式口吻，助人心理驱动 |

**Anki 让你记住答案的形状，Engram 让你拥有知识本身。**

## 学习科学基础

研究表明的学习效果金字塔（从差到优）：

```
生成性学习（自己写、讲、教）  ← 最有效 | 天花板在这层
       ↑
    主动回忆 + 间隔重复
       ↑
    重读、划线                  ← 最常见但最无效
```

**Engram 的目标：** 覆盖整个光谱。不只停在中间层的"主动回忆"，而是让生成性学习变得日常化。

## 架构

**四层结构** (自上而下)：

```
┌─────────────────────────────────────┐
│ Schema（配置层）                     │  告诉 LLM 怎么维护 Wiki、生成活动、说话
├─────────────────────────────────────┤
│ Wiki（知识层）                       │  LLM 生成和维护的 Markdown 文件
├─────────────────────────────────────┤
│ Learning（学习层）                   │  多模式活动 + FSRS 调度 + 多通道推送
├─────────────────────────────────────┤
│ Raw Sources（源材料）                │  你策展的文章、论文、笔记，不可变
└─────────────────────────────────────┘
```

**四个核心操作**：

| 操作 | 作用 | 输出 |
|------|------|------|
| **Ingest** | 丢一个源材料进去，LLM 读完、更新 Wiki、生成学习活动 | Wiki + 活动队列 |
| **Query** | 你提问，LLM 从 Wiki 综合回答，好的回答回写 Wiki | 答案 + Wiki 更新 |
| **Review** | 系统推送学习活动，你回忆/解释/应用，反馈更新 FSRS | 学习反馈 |
| **Lint** | LLM 定期检查 Wiki：矛盾、孤立、过时、缺失链接 | 维护建议 |

**两个导航文件**：

- `index.md` — 按内容组织，每页一行摘要。规模不大时比向量检索好用
- `log.md` — 按时间追加，记录所有 ingest/query/review 活动。`grep` 一下就能看最近发生了什么

## 知识质量管理

**底线：知识库里的数据不能出错。** 有错误的知识库比没有知识库更危险——用户信了错数据，项目里出事。

### 问题

单个 LLM 单次提取，天然有盲区。一张复杂表格，模型可能在某行看串了、某列对错了，但它很自信地输出结果，看不出自己错了。

### 方案：多角色交叉验证

同一源材料经过多个角色处理，互相验证。不是投票，而是**第三个角色专门负责找矛盾**。

```
源材料（表格截图）
    ├─→ Agent A（严格型）
    │    规则："逐行逐列精确提取，不确定标 NULL，不要猜"
    │    输出：{material_cost: 405, machine_cost: NULL}
    │
    ├─→ Agent B（理解型）
    │    规则："理解整体结构后提取，允许合理推断，标注依据"
    │    输出：{material_cost: 450, machine_cost: 80}
    │
    └─→ Agent C（审计型）
         规则："对比 A 和 B，找出不一致，分析原因，给出判断"
         输出：{material_cost: 405, machine_cost: 80,
                conflicts: "material_cost 不一致，A=405 B=450，建议采用 A，
                B 可能看串了第 3 行和第 4 行"}
```

### 置信度分级

审计员的输出包含每个字段的置信度，决定数据怎么处理：

```
high（三个 agent 一致或审计员高度确信）
    └─→ 直接入库，生成学习活动

medium（两个不一致，审计员有倾向）
    └─→ 入库但标记待验证，不生成活动（避免教错）

low（三个都不确定或审计员无法判断）
    └─→ 不入库，放入待审核队列，通知用户
```

### Wiki 中的呈现

```markdown
# 码头工程 - 基槽挖泥定额

| 项目 | 一类费 | 二类费 | 置信度 |
|------|--------|--------|--------|
| 挖泥船 450m³/h | 850 | 320 | ✓ high |
| 挖泥船 980m³/h | 1200 | 405 | ⚠️ medium |

> **来源：** 码头定额.pdf 第 38 页  
> **提取方式：** 三角色交叉验证  
> **审计备注：** 980m³/h 的二类费在两个 agent 间有分歧，建议核实原始 PDF
```

### 成本优化

不是每次都跑满三轮：

```
简单内容（纯文字，结构清晰）        → 单角色，省成本
复杂内容（表格、图表、合并单元格）  → 双角色 + 审计员
关键数据（金额、公式、法律）        → 多角色 + 人工审核

智能触发：先跑一个角色，检查输出质量。
没问题直接入库，有问题再触发第二角色。


## 学习活动类型

不只是"Q: __ A: __"。所有活动都通过 FSRS 调度。

| 活动类型 | 形式 | 心理机制 | 例子 |
|---------|------|---------|------|
| **事实卡片** | 定义、公式、关键数据 | 识别 | "FSRS 是什么？" |
| **费曼挑战** | "用自己的话解释 XX" | 生成效应 | "解释梯度下降。" |
| **连接挑战** | 发现和联系多个领域的概念 | 知识网络 | "注意力机制和 CNN 处理序列的区别？" |
| **情境应用** | 在真实场景中应用知识 | 转移学习 | "评估方案时如何避免确认偏误？" |
| **教学模拟** | "讲解给同事听"，LLM 给反馈 | 教学效应 | "用 2 分钟讲清 Transformer。" |

**共性：** 所有活动都需要主动输出，都被调度，都与 Wiki 关联。

## 人格化推送

这是 Engram 和所有间隔重复工具最大的区别。不是"考官问题"，而是"朋友请教"。

### 对比

**传统方式：**
```
Bot："请回答：水运定额中一类费和二类费的区别？"
用户：[关闭]
```

**Engram 方式：**
```
Bot："诶 peter，我最近在看水运定额，有个地方没想明白。
     为什么要把费用分成一类费和二类费啊？直接统一算不行吗？
     你是搞这块的，能给我讲讲不？"
用户：这个我知道，来讲讲。（自觉参与）
```

**心理学原理：** 助人效应。当人觉得自己在帮别人时，会更主动地组织语言、抓重点、举例子。用户以为自己在帮朋友，实际在做费曼练习。

### 对话示例

```
编程：
  "我昨天看 Go 源码，发现处理并发用的是 channel 不是锁。
   我有点搞不懂 channel 比 mutex 好在哪？你写 Go 多了应该比我清楚吧？"

心理学：
  "我最近读到确认偏误——你天然会找支持自己想法的证据。
   但做产品调研时怎么才能避免这个？你有经验没？"

历史：
  "秦始皇统一度量衡。但我一直困惑，真的对经济影响那么大吗？
   还是后人夸大了？你对这块熟不熟？"
```

### 回复处理

**用户答对了：** 不说"恭喜答对"，Bot 说"原来如此"，自然追问：

```
用户："一类费是固定的跟机械走，二类费是浮动的跟市场走。"

Bot："哦我明白了。所以定额编制时一类费就定死了，
     二类费要乘当地实际价格对吧？
     那油价涨很多，实际造价就会比定额算出来的高很多吧？"
```

**用户答不上来：** 不公布答案，Bot 分享"自己的发现"让对方验证：

```
用户："呃...不太确定。"

Bot："没事没事，我也查了半天。有个说法是一类费主要是机械本身
     的费用——折旧维修这些，二类费是用机械时候的消耗，比如人工和油钱。
     你帮我看看这个对不对？"
```

### 人格配置示例

```yaml
bot_name: "小安"

personality:
  role: "正在学习知识的朋友"
  tone: "口语化、自然、偶尔犯迷糊"
  relationship: "请教者，不是考官"

rules:
  - 永远以"我遇到了一个问题"的口吻提问
  - 不出现"请回答""测试""复习"这些词
  - 可以表达困惑和不确定
  - 用户答对要真诚感谢，不是打分
  - 用户答不上来要主动分享"发现"，不是公布答案
  - 追问要自然，像"真的吗？那 XX 呢？"
```

## 多通道推送

核心理念：**不要让用户来找知识，让知识去找用户。**

### 推送通道

| 通道 | 形式 | 场景 | 优先级 | 为什么 |
|------|------|------|--------|--------|
| **终端** | 文字 | 开终端时自动显示 | P0 | 开发者日常流程，零成本 |
| **QQ Bot** | 文字 + 语音 | 碎片时间 | P0 | 主要使用人群 |
| **Telegram** | 文字 + 语音 | 碎片时间 | P1 | 备选通道 |
| **浏览器扩展** | 文字 | 新标签页 | P2 | 被动曝光 |
| **IDE 插件** | 弹窗 | 编码中 | P3 | 上下文相关 |

### 终端推送

每次打开终端，自动弹一条。Shell 脚本加到 `.zshrc` / `.bashrc`，零依赖。

```
┌─ Engram ──────────────────────────────────────┐
│                                                │
│  💡 小安想请教你：                               │
│                                                │
│  "FSRS 的核心参数有哪四个啊？                    │
│   我老是记混 stability 和 retrievability 的区别" │
│                                                │
│  [Enter 查看]  [Esc 跳过]  [c 标记已掌握]        │
│  今日进度: 3/15  │  连续打卡: 12 天              │
└────────────────────────────────────────────────┘
```

### QQ Bot 推送

**语音是关键。** 文字需要看屏幕集中注意力，语音不用——走路、等电梯、洗碗时点一下听 30 秒就完事。语音的心理效果更像朋友聊天。

推送时间表：

```
早上通勤   → 语音，请教一个新问题（5-10 分钟理解）
中午午休   → 文字，费曼挑战（简短输出）
晚上睡前   → 语音，今日知识回顾串联（回顾形式，较轻松）
```

### 调度引擎

```
FSRS 计算到期 + 时间策略 + 通道选择 + 活动类型 + 微习惯保护
            ↓
        推送决策
            ↓
    ┌───────┼───────┐
    ▼       ▼       ▼
  终端    QQ Bot  Telegram
```

## 心理设计

间隔重复 app 最大的杀手不是技术问题，是**心理问题**。

| 陷阱 | Engram 的解决 |
|------|---------|
| 考官心态，用户本能逃避 | 朋友式口吻，助人心理驱动 |
| 习惯形成难，需要主动打开 | 主动推送，知识找用户 |
| 积压数字恐怖，劝退用户 | 微习惯：默认每天 1 个，可选加量，不显示总数 |
| 失败感和罪恶感 | 断了不惩罚，连续天数不强硬，可随时跳过 |
| 推送骚扰 | 不在深夜/会议推，允许跳过，完全可控 |

## 快速开始

### 1. 本地开发环境

```bash
git clone https://github.com/YOUR_USERNAME/engram.git
cd engram

# Python 虚拟环境
python -m venv venv
source venv/bin/activate  # Linux/Mac
# or
venv\Scripts\activate      # Windows

pip install -r requirements.txt

# 配置环境变量
cp .env.example .env
# 编辑 .env：填入 LLM API Key、QQ Bot Token 等
```

### 2. 启动服务

```bash
# 用 Docker Compose（推荐）
docker-compose up -d

# 或手动启动各个服务
python bot/server.py &          # Bot 推送服务
python ingest/pipeline.py &     # Ingest 管道（可选）
```

### 3. 常用命令

```bash
# 摄入新文章（单角色，快速）
python ingest/pipeline.py raw/articles/xxx.md

# 摄入 PDF（多角色交叉验证）
python ingest/pipeline.py --multiagent raw/papers/xxx.pdf

# 浏览知识库
open wiki/               # Finder
# 或用 Obsidian 打开 wiki/ 目录（推荐）

# 今日学习（终端复习）
python tools/review.py

# Wiki 健康检查（找矛盾、孤立页面）
python tools/lint.py
```

### 4. 集成到终端

编辑 `~/.zshrc` 或 `~/.bashrc`：

```bash
# 每次打开终端显示一条 Engram 推送
if command -v python &> /dev/null; then
  python ~/.engram/terminal_push.py
fi
```

## 技术选型

| 组件 | 选择 | 为什么 | 备注 |
|------|------|--------|------|
| **存储** | Markdown + Git | 可读性好、版本控制、Obsidian 原生支持 | 小规模适合，大规模可迁移数据库 |
| **间隔重复** | FSRS | 比 SM-2 高效 30%+，开源 | [FSRS 文档](https://github.com/open-spaced-repetition/fsrs4anki) |
| **Wiki 浏览** | Obsidian | 图谱视图、双向链接、插件生态 | 可选自建 TiddlyWiki |
| **QQ Bot** | NapCat / Lagrange | 活跃维护，支持语音消息 | 两个都可选 |
| **TTS** | MiMo / Edge TTS | 中文语音质量好，可自托管 | 优先 MiMo |
| **视觉识别** | MiMo Omni | 多模态，表格/图表识别强 | 备选 Claude Vision |
| **文本推理** | Claude / MiMo | 逻辑推理强，适合审计员 | Claude 更擅长对比分析 |
| **搜索** | BM25（自建） | 本地搜索，无外部依赖 | 规模大可升级到 MeiliSearch |
| **部署** | Docker Compose | 一键启动 | 可升级到 K8s |

## 路线图

### 第一阶段：MVP（最小化可行产品） — 3 周
**目标：** 跑起来一个完整的闭环（单用户本地版）

- [ ] Wiki 结构和规范定义（CONVENTIONS.md）
- [ ] 单角色 Ingest 管道（PDF / 文章 → Wiki + 活动）
- [ ] FSRS 调度核心（deck.json 数据结构）
- [ ] 终端推送（shell 脚本注入）
- [ ] QQ Bot 基础（文字推送 + 人格化语气）

**验收标准：** 能完整走通一次"摄入→学习→推送→回复"的全流程

---

### 第二阶段：多角色 + 语音 — 4 周
**目标：** 加入知识质量管理，支持语音交互

## FAQ

### Q: 跟 Obsidian + Anki 组合比怎么样？

**Obsidian：** 很好的 Wiki 浏览工具，但不参与学习调度。  
**Anki：** 很好的间隔重复引擎，但学习模式单一（Q/A 卡片）。

Engram 把两者结合了，并且：
- 学习不局限于 Q/A，有费曼、连接、应用多种模式
- 推送主动找你，而不是你主动打开 app
- 知识质量由多角色验证保证

### Q: 成本会不会很高？

**第一阶段（MVP）：** 成本很低，单角色提取，省 API 调用。  
**第二阶段（多角色）：** 确实是三倍成本，但有按需触发的优化。  
**长期：** 随着用户增多和 API 价格下降，成本可接受。

### Q: 能不能离线使用？

**Wiki 浏览：** 完全离线，就是 Markdown 文件。  
**推送和审计：** 需要 LLM API 和 Bot 服务，无法离线。  

可以考虑本地部署开源模型（Ollama / LLaMA），但推荐用 API。

### Q: 能不能集成我自己的学习内容？

可以。Engram 的 Ingest 管道可以处理：
- Markdown 文章
- PDF（含表格、图表）
- 网页链接（爬取后处理）
- 自己的笔记

提交到 `raw/` 目录，运行 `python ingest/pipeline.py` 即可。
